Cryptographic Architecture & Transparency

Technical specification of algorithms, parameters, binary file packaging, and threat model.

1. Zero-Knowledge Threat Model

Secure Backup is engineered under the fundamental assumption that any network transmission or untrusted remote storage provider (such as Google Drive) may be subject to surveillance, data breaches, or insider access. To provide absolute privacy:

  • No Server-Side Knowledge: The user's passphrase, derived symmetric keys, file names, directory structures, and file contents are never transmitted across any network in plaintext.
  • Autonomous Client Operation: All cryptographic operations happen exclusively in the local desktop process using pure Rust cryptography crates compiled into the native binary.

2. Key Derivation: Argon2id

Master symmetric keys are never stored on disk. Instead, when a user enters their passphrase, a 256-bit AES key is deterministically derived using the memory-hard Argon2id algorithm (RFC 9106, version 0x13):

  • Memory Cost (m_cost): 19,456 KiB (19 MiB RAM)
  • Time Cost (t_cost / iterations): 2 passes over memory
  • Parallelism (p_cost / lanes): 1 thread lane
  • Salt: 16-byte cryptographically random salt generated using the OS CSPRNG (rand::rngs::OsRng)
  • Key Output Length: 32 bytes (256 bits)

This configuration creates extreme computational resistance against GPU/ASIC brute-force dictionary attacks while maintaining sub-second latency on standard desktop CPUs.

3. Symmetric Authenticated Encryption: AES-256-GCM

File content and snapshot manifests are encrypted using AES-256-GCM (Galois/Counter Mode). AES-GCM is an Authenticated Encryption with Associated Data (AEAD) standard that provides both confidentiality and verifiable authenticity.

  • Nonce Isolation: A fresh, cryptographically secure 12-byte (96-bit) nonce is generated for every single file. Reusing a nonce with the same key would compromise GCM authentication; generating fresh nonces per file guarantees nonce uniqueness.
  • AEAD Authenticator Tag: A 16-byte polynomial authentication tag is appended to every ciphertext payload. If a single bit in the ciphertext, salt, or nonce is altered (bit-flip attack or bit-rot), the authentication tag verification fails immediately and no decrypted data is written to disk.

4. Encrypted Binary File Format

Every encrypted file in a Secure Backup archive follows a standardized binary container structure:

[ MAGIC HEADER (8 Bytes: "SECBKP01") ]
[ ARGON2 SALT (16 Bytes) ]
[ AES-GCM NONCE (12 Bytes) ]
[ CIPHERTEXT PAYLOAD (Variable length) + AEAD TAG (16 Bytes) ]

This self-contained structure allows independent verification and recovery of individual files even if external manifest indexes are unavailable.

5. Manifest Authenticity & Substitution Defenses

When a backup is created, the list of file paths, sizes, timestamps, and pre-encryption SHA-256 integrity digests is serialized to JSON and encrypted using the same master key into manifest.enc. During restore:

  • The manifest is decrypted and validated against its AEAD tag.
  • Each restored file is verified post-decryption against its recorded SHA-256 hash.
  • Path traversal protections reject any relative (../) or absolute paths in the manifest.
